# AI Data Migration Assistant

Moves messy booking data from an old spreadsheet or a HubSpot CRM into a clean system. AI suggests how the columns map, a person confirms them, and Python cleans, validates and migrates the data into Airtable, then produces a migration report.

> All data in this repo is synthetic and generated by script. No real company or customer data is used.

**Live demo:** https://ai-data-migration-assistant.streamlit.app/

---

## The problem

At Emirates I did source-to-target mapping by hand. It was tedious, with lots of codes to match across systems, and I built a 200+ term business glossary just so data definitions lined up.

Every migration has the same steps: work out which old column matches which new field, fix the formats, find the duplicates, chase the missing values, move the data, and then explain what happened. This project automates the repetitive parts and keeps a person in control of the decisions.

## How it works

```
Messy CSV  ──┐
             ├──► 1. Profile with SQL (SQLite) ──► how messy is it?
HubSpot CRM ─┘
                    │
                    ▼
             2. AI suggests mappings (Gemini) ──► source column → target field, confidence, reason
                    │
                    ▼
             3. Person reviews and confirms ──► nothing moves without this
                    │
                    ▼
             4. Clean and validate (pandas)
                    │
                    ├──► Clean rows ──► 5. Migrate to Airtable (REST API) ──► 6. Report
                    │
                    └──► Flagged rows ──► shown for review, never deleted
```

### 0. Choose a source

The app can start from either:

- **Upload CSV:** any CSV file, or the included sample (`sample_data/messy_bookings.csv`).
- **Pull from HubSpot:** `hubspot_source.py` reads contacts from the HubSpot CRM REST API with a service key (read-only scopes), following HubSpot's paging cursor until every contact is fetched. In the demo account, the data sits in HubSpot's own fields (`lastname`, `email`, `phone`) plus custom ones (`destination`, `booked_on`, `travel_dt`, `price`, `booking_status`), still messy.

HubSpot has its own connector file (`hubspot_source.py`), and the CSV upload is read in `app.py`. Both produce the same kind of table, so everything after this step works the same for both.

### 1. Profile with SQL

The data is loaded into a local SQLite database (`migration.db`) exactly as it is. SQL queries then measure the mess before anything is changed, using whatever column names the source has:

- total number of rows
- missing or blank values in each column
- fully duplicated rows
- the different values in short-list columns like status, and how often each appears

### 2. AI suggests the mappings

Only the column names and 3 sample rows are sent to the Google Gemini API, never the whole file, together with the target fields and their descriptions from `schema.py`. Gemini replies in JSON with, for each source column:

- the target field it most likely matches (or none)
- a confidence level (high / medium / low)
- a short reason

The suggestions are checked in code: every target must be a real field, and no field can be used twice.

Gemini is asked **once per file or HubSpot pull**, and the answer is remembered, so clicking around the page doesn't use extra requests. It's only asked again when the user clicks **Ask Gemini again**. If Gemini is busy or the free daily limit is used up, the app says so clearly and the user can type the mappings by hand.

### 3. A person confirms

The suggestions appear in an editable table. The user can accept or change any of them, and the data is only renamed and cleaned after they click **Confirm**.

### 4. Clean and validate

Python (pandas) fixes what it safely can:

| Field | Cleaning rule |
| --- | --- |
| `customer_name` | Trim spaces, title case |
| `email` | Trim, lowercase |
| `phone` | Convert to international format, e.g. `+971501234567`, `+442079460958`. Numbers without a country code are treated as UAE numbers |
| `destination` | Trim spaces |
| `booking_date`, `travel_date` | Convert to `YYYY-MM-DD` |
| `amount_aed` | Convert `AED 1,200`, `1200`, `1.2k` to a number |
| `status` | Standardise to `Confirmed`, `Pending` or `Cancelled` |

Then it checks the rules of the target schema and **flags** any row that breaks them, with the reason in plain English:

- missing customer name, destination or booking date
- invalid email
- travel date not after the booking date
- missing or non-positive amount
- amount that isn't a number (e.g. `free`)
- phone number, booking date or travel date that is filled in but can't be understood
- status that isn't one of the allowed values
- likely duplicate: same customer name (ignoring case, spaces and small typos) and same email or phone. **Both rows of a pair are flagged**, each saying which row it matches, so a person chooses which one to keep.

### 5. Migrate to Airtable

Clean rows are sent to Airtable through its REST API, using a personal access token that can only read and write one base. Records go in batches of 10 (Airtable's limit per request). If a batch fails, the run doesn't stop: the failed rows and Airtable's error message are recorded and the next batch continues. Every row's result is logged in a `migration_log` table in SQLite.

### 6. Report

A migration summary showing records in the source, fields mapped, what was cleaned, what was flagged and why, and what was migrated or failed. The migrated and failed numbers, the failure reasons and the time of the run are read with SQL from the migration log; the numbers for mapping, cleaning and flagging come from the cleaning step. The summary can be downloaded as Markdown, and the details as a CSV with one line per record, including the flagged rows.

## Design choices

**Why a person confirms the AI's mappings:** AI suggestions can be wrong. If a wrong mapping went through unchecked, say price into phone, every record would land in the new system with the wrong data, and fixing that inside a customer's live system is much harder than catching it before anything moves.

**Why flagged rows aren't deleted:** flagged rows are important for customers because they are real entries that need to be investigated, not thrown away.

**Why only 3 sample rows go to the AI:** column names plus a few examples are enough to suggest a mapping, and sending less data keeps customer data exposure to a minimum.

**Why separate connectors:** each source (CSV, HubSpot) only has to produce a table. Mapping, cleaning, migration and the report don't change, so adding another source means adding one file and one option in `app.py`.

**Why SQLite:** the database is only a staging and logging layer for one user, and it needs no setup, so anyone can clone and run the project. In a larger, multi-user deployment I would use PostgreSQL; the queries would barely change.

**Keys and access:** API keys live in a local `.env` file (or Streamlit Secrets when deployed) and are never committed. The Airtable token is limited to the scopes and the one base the tool needs, and the HubSpot key is read-only.

## Testing the APIs

The `postman/` folder has a Postman collection used to test the APIs by hand before writing the code:

- **Airtable:** list records, create a record, delete a record
- **HubSpot:** list contacts with the properties the app uses

Keys are not in the file. Set `base_id`, `token` and `hubspot_token` as Postman environment variables, and `record_id` for the record to delete.

Error cases tested: a bad token returns `401`, an unknown field name returns `422 UNKNOWN_FIELD_NAME`, and deleting a record that doesn't exist returns `403` (Airtable doesn't reveal whether a record exists).

## Known issues and fixes

Problems found while testing, tracked as GitHub issues:

| Issue | Problem | Fix |
| --- | --- | --- |
| [#1](https://github.com/Saif-87/ai-data-migration-assistant/issues/1) | Phone cleaning only accepted UAE numbers | Keep other countries' codes; UAE is the default for local numbers |
| [#2](https://github.com/Saif-87/ai-data-migration-assistant/issues/2) | The SQL profile only worked with the sample file's column names | Generic queries that work with any columns, including HubSpot data |
| [#3](https://github.com/Saif-87/ai-data-migration-assistant/issues/3) | The duplicate check kept the first row even when it was the misspelled one | Flag both rows so a person chooses |
| [#4](https://github.com/Saif-87/ai-data-migration-assistant/issues/4) | Gemini was asked again when switching sources, using up the free daily limit | Ask once per file and remember the answer |
| [#5](https://github.com/Saif-87/ai-data-migration-assistant/issues/5) | UAE landline numbers were cleaned into wrong numbers (e.g. `04 123 4567` → `+971041234567`) | Accept 8-digit landlines as well as 9-digit mobiles: `04 123 4567` → `+97141234567` |

## Sample data

`generate_data.py` creates `sample_data/messy_bookings.csv`: 100 fake travel bookings made with the Faker library, made messy on purpose:

| Problem | Example |
| --- | --- |
| Inconsistent column names | `Cust Name`, `E-mail`, `Dest.`, `travel dt` |
| Mixed date formats | `03/10/2026`, `2026-10-03`, `3 Oct 26` |
| Prices written differently | `AED 1,200`, `1200`, `1.2k` |
| Phone numbers with and without country code | `+971 50 123 4567`, `050 123 4567`, `501234567` |
| Duplicate customers with small spelling differences | `Alexander Date` vs `ALEXANDER DATE`, `Vritti Badal` vs `Vitti Badal` (each duplicate appears twice) |
| Missing values | Blank emails and booking dates |

It uses a fixed random seed, so it produces the same file every time. The same file was imported into HubSpot for the HubSpot demo; HubSpot didn't import 7 rows whose email was already used ("Duplicate alternate ID, 7 values not imported"), so it holds 93 contacts.

## Target schema

| Field | Type | Rule |
| --- | --- | --- |
| `customer_name` | text | Required, title case |
| `email` | text | Valid format, lowercase |
| `phone` | text | International format with country code |
| `destination` | text | Required |
| `booking_date` | date | Required, `YYYY-MM-DD` |
| `travel_date` | date | `YYYY-MM-DD`, must be after `booking_date` |
| `amount_aed` | number | Numeric, positive |
| `status` | text | One of `Confirmed`, `Pending`, `Cancelled` |

## Run it locally

You need:

- Python 3.14
- a free Google AI Studio API key
- a free Airtable account with a table called `Bookings` whose fields match `schema.py`: `amount_aed` as a **number** field, `booking_date` and `travel_date` as **date** fields (ISO format, no time), and the rest as single line text (`email` can be an email field)
- optional: a free HubSpot account and a service key with `crm.objects.contacts.read` and `crm.schemas.contacts.read`, for the HubSpot source

```
git clone https://github.com/Saif-87/ai-data-migration-assistant.git
cd ai-data-migration-assistant
python -m venv .venv
source .venv/Scripts/activate      # Windows (Git Bash)
pip install -r requirements.txt
cp .env.example .env               # then add your keys to .env
python generate_data.py
streamlit run app.py
```

`.env` needs these values (`HUBSPOT_TOKEN` only if you use the HubSpot source):

```
GEMINI_API_KEY=
AIRTABLE_TOKEN=
AIRTABLE_BASE_ID=
HUBSPOT_TOKEN=
```

## Limitations

- Built and tested on synthetic data for one scenario (travel bookings into Airtable).
- Gemini's free tier allows a limited number of requests per day; when it runs out, mappings have to be typed by hand. There's no automatic retry yet when Gemini is busy.
- On Streamlit Community Cloud, the SQLite log resets when the app restarts; a production version would keep the log in a hosted database.
- Duplicate detection uses simple rules, so unusual spelling differences can be missed.

## Hardest part

The hardest parts were the problems that look simple at first: duplicates, wrong mappings, deciding what should be flagged, and misspelled names. Some were rookie mistakes. My first duplicate check kept whichever row came first, even when that was the misspelled one ([#3](https://github.com/Saif-87/ai-data-migration-assistant/issues/3)), and the app used up Gemini's free limit because it asked again more often than it needed to ([#4](https://github.com/Saif-87/ai-data-migration-assistant/issues/4)).

Getting HubSpot to work was the most frustrating part. HubSpot had changed how API access works (private apps were replaced by service keys), and the import put names and phone numbers into HubSpot's own fields instead of the ones I created, so I had to find the real property names before the code could read them.

## What I'd add next

Make it more efficient: one click of a button to pull, map, clean and migrate, without switching between tabs, with a person stepping in only where they're needed (low-confidence mappings and flagged rows).

- Automatic retries when Gemini is busy
- More sources, such as Salesforce and Google Sheets
- Scheduled syncs, so new records move over on their own
