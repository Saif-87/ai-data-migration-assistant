# AI Data Migration Assistant

Moves messy booking data from an old spreadsheet into a clean system. AI suggests how the columns map, a person confirms them, and Python cleans, validates and migrates the data into Airtable, then produces a migration report.

> All data in this repo is synthetic and generated by script. No real company or customer data is used.

## The problem

At Emirates I did source-to-target mapping by hand. It was tedious, with lots of codes to match across systems, and I built a 200+ term business glossary just so data definitions lined up.

Every migration has the same steps: work out which old column matches which new field, fix the formats, find the duplicates, chase the missing values, move the data, and then explain what happened. This project automates the repetitive parts and keeps a person in control of the decisions.

## How it works

```
Messy CSV
   │
   ▼
1. Profile with SQL (SQLite) ──► how messy is it?
   │
   ▼
2. AI suggests mappings (Gemini) ──► source column → target field, confidence, reason
   │
   ▼
3. Person reviews and confirms ──► nothing moves without this
   │
   ▼
4. Clean and validate (pandas)
   │
   ├──► Clean rows ──► 5. Migrate to Airtable (REST API) ──► 6. Report
   │
   └──► Flagged rows ──► shown for review, never deleted
```

### 1. Upload and profile with SQL

The uploaded CSV is loaded into a local SQLite database (`migration.db`) exactly as it is. SQL queries then measure the mess before anything is changed:

- total number of rows
- rows with a missing email or booking date
- emails and phone numbers that appear more than once (likely duplicates)
- every different way the status is written, and how often

These queries use the sample file's column names (`E-mail`, `Booked On`, `phone_no`, `STATUS`). For a file with different column names, the app skips the profile and the rest of the steps still work.

### 2. AI suggests the mappings

Only the column names and 3 sample rows are sent to the Google Gemini API, never the whole file, together with the target fields and their descriptions from `schema.py`. Gemini replies in JSON with, for each source column:

- the target field it most likely matches (or none)
- a confidence level (high / medium / low)
- a short reason

The suggestions are then checked in code: every target must be a real field, and no field can be used twice.

### 3. A person confirms

The suggestions appear in an editable table. The user can accept or change any of them, and the data is only renamed and cleaned after they click **Confirm**.

### 4. Clean and validate

Python (pandas) fixes what it safely can:

| Field | Cleaning rule |
| --- | --- |
| `customer_name` | Trim spaces, title case |
| `email` | Trim, lowercase |
| `phone` | Convert to international format, e.g. `+971501234567`. Numbers without a country code are treated as UAE numbers |
| `booking_date`, `travel_date` | Convert to `YYYY-MM-DD` |
| `amount_aed` | Convert `AED 1,200`, `1200`, `1.2k` to a number |
| `status` | Standardise to `Confirmed`, `Pending` or `Cancelled` |

Then it checks the rules of the target schema and **flags** any row that breaks them, with the reason in plain English:

- missing customer name, destination or booking date
- invalid email
- travel date not after the booking date
- missing or non-positive amount
- amount that isn't a number (e.g. `free`)
- phone number, booking date or travel date that is filled in but can't be understood
- status that isn't one of the allowed values
- likely duplicate: same customer name (ignoring case, spaces and small typos) and same email or phone

### 5. Migrate to Airtable

Clean rows are sent to Airtable through its REST API, using a personal access token that can only read and write one base. Records go in batches of 10 (Airtable's limit per request). If a batch fails, the run doesn't stop: the failed rows and Airtable's error message are recorded and the next batch continues. Every row's result is logged in a `migration_log` table in SQLite.

### 6. Report

A migration summary showing records in the source file, fields mapped, what was cleaned, what was flagged and why, and what was migrated or failed. The migrated and failed numbers, the failure reasons and the time of the run are read with SQL from the migration log; the numbers for mapping, cleaning and flagging come from the cleaning step. The summary can be downloaded as Markdown, and the details as a CSV with one line per record, including the flagged rows.

## Design choices

**Why a person confirms the AI's mappings:** [your words — e.g. AI suggestions can be wrong, and a migration error damages customer trust]

**Why flagged rows aren't deleted:** flagged rows are important for customers because they are real entries that need to be investigated, not thrown away.

**Why only 3 sample rows go to the AI:** column names plus a few examples are enough to suggest a mapping, and sending less data keeps customer data exposure to a minimum.

**Why SQLite:** the database is only a staging and logging layer for one user, and it needs no setup, so anyone can clone and run the project. In a larger, multi-user deployment I would use PostgreSQL; the queries would barely change.

**Keys and access:** API keys live in a local `.env` file (or Streamlit Secrets when deployed) and are never committed. The Airtable token is limited to the scopes and the one base the tool needs.

## Sample data

`generate_data.py` creates `sample_data/messy_bookings.csv`: 100 fake travel bookings made with the Faker library, made messy on purpose:

| Problem | Example |
| --- | --- |
| Inconsistent column names | `Cust Name`, `E-mail`, `Dest.`, `travel dt` |
| Mixed date formats | `03/10/2026`, `2026-10-03`, `3 Oct 26` |
| Prices written differently | `AED 1,200`, `1200`, `1.2k` |
| Phone numbers with and without country code | `+971 50 123 4567`, `050 123 4567`, `501234567` |
| Duplicate customers with small spelling differences | `Alexander Date` vs `ALEXANDER DATE`, `Vritti Badal` vs `Vitti Badal` (each duplicate appears twice) |
| Missing values | Blank emails and booking dates |

It uses a fixed random seed, so it produces the same file every time.

## Target schema

| Field | Type | Rule |
| --- | --- | --- |
| `customer_name` | text | Required, title case |
| `email` | text | Valid format, lowercase |
| `phone` | text | International format with country code |
| `destination` | text | Required |
| `booking_date` | date | Required, `YYYY-MM-DD` |
| `travel_date` | date | `YYYY-MM-DD`, must be after `booking_date` |
| `amount_aed` | number | Numeric, positive |
| `status` | text | One of `Confirmed`, `Pending`, `Cancelled` |

## Project files

| File | What it does |
| --- | --- |
| `app.py` | The Streamlit page that runs the whole flow |
| `generate_data.py` | Creates the synthetic messy CSV |
| `schema.py` | Defines the 8 target fields, their descriptions and rules |
| `database.py` | Loads the CSV into SQLite, profiles it with SQL, and holds the migration log |
| `mapping.py` | Asks Gemini for suggested field mappings and checks them |
| `cleaning.py` | Cleans, validates and flags rows |
| `migrate.py` | Sends clean rows to Airtable through its REST API |
| `report.py` | Builds the migration report |
| `.env.example` | Lists the keys needed, with no real values |

## Run it locally

You need Python 3.14, a free Google AI Studio API key, and a free Airtable account with a table called `Bookings` whose fields match `schema.py`.

```
git clone https://github.com/Saif-87/ai-data-migration-assistant.git
cd ai-data-migration-assistant
python -m venv .venv
source .venv/Scripts/activate      # Windows (Git Bash)
pip install -r requirements.txt
cp .env.example .env               # then add your keys to .env
python generate_data.py
streamlit run app.py
```

`.env` needs three values:

```
GEMINI_API_KEY=
AIRTABLE_TOKEN=
AIRTABLE_BASE_ID=
```

## Limitations

- Built and tested on synthetic data for one scenario (travel bookings into Airtable).
- On Streamlit Community Cloud, the SQLite log resets when the app restarts; a production version would keep the log in a hosted database.
- Duplicate detection uses simple rules, so unusual spelling differences can be missed.
